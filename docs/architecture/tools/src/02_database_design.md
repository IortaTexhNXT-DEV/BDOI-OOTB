# Introduction

## Purpose and scope

This document describes the logical and physical design of the BrokerVerse database: the schema organised by business domain, the entity-relationship structure of each domain, the key tables and their keys, the use of JSONB document columns, document numbering, audit and soft-delete conventions, the migration and seed approach, and the handling of time zones, dates and amounts. The table-by-table inventory with sizes, row counts and retention classes is document 03.

Sources: `backend/src/db/migrations/*.sql` (32 files, 1,678 lines), `backend/src/db/seeds`, `backend/src/db/pool.js`, `migrate.js`, `seed.js`, `backend/src/lib/dates.js`, `money.js`, and the catalogue of the local PostgreSQL 16 database `brokerverse` (snapshot in `docs/architecture/tools/data/db_snapshot.json`).

## Database platform

{generate: db_facts}

One database and one schema (`public`) hold all data. The application connects with a single login through `DATABASE_URL` (node-postgres pool, maximum 10 connections per API process). The login needs rights to create tables because the API applies its own migrations on start. Only the `pgcrypto` extension is used (for `gen_random_bytes()` in primary-key defaults).

# Design conventions

## Keys

{widths: 26,74}
| Convention | Detail |
|---|---|
| Business records | 43 tables use a text primary key made of a readable prefix and 16 (or 12) random hexadecimal characters, generated by the database: for example `policies.id DEFAULT 'pol_' \|\| encode(gen_random_bytes(8), 'hex')`. Prefixes include `ld_` lead, `cl_` client, `qt_` quotation, `pol_` policy, `end_` endorsement, `clm_` claim, `rnw_` renewal, `or_` receipt, `jv_` journal voucher, `pv_` payment voucher, `rm_` remittance, `dn_` debit note, `usr_` user, `doc_` document. The ids are not guessable and never collide across tables. |
| Reference and log tables | 46 tables use integer or bigint serial keys (masters such as countries, banks, insurers, products; and high-volume children and logs such as `journal_lines`, `audit_log`, `login_history`, `job_runs`, `claim_history`). |
| Natural and composite keys | `app_settings(key)`, `gl_accounts(code)`, `master_types(code)`, `report_definitions(code)`, `accounting_periods(period)`, `incentive_calculations(batch_id)`, `refresh_tokens(jti)`, `schema_migrations(name)`, `sequences(name, period)`, `role_permissions(role_id, permission_id)`, `user_roles(user_id, role_id)`. |
| Business numbers | Human-readable document numbers (`QT-2026-00001`, `POL-2026-00001`, `OR-2026-00019`) are separate unique columns (`quote_number`, `policy_number`, `receipt_number`, `jv_number`...), never primary keys; the API accepts either the id or the number on most detail endpoints. |
| Foreign keys | 174 foreign keys: 144 `NO ACTION` (a referenced record cannot be deleted while used), 26 `CASCADE` (children that have no meaning without their parent: journal lines, receipt lines, claim history, renewal notices, role grants, refresh tokens, notifications ...) and 4 `SET NULL`. |

## Column types

{widths: 26,74}
| Data | Type and handling |
|---|---|
| Amounts | `numeric` (178 columns), typically `numeric(14,2)` or unconstrained; converted to JavaScript numbers by the pool type parser (`pg.types.setTypeParser(1700, Number)`); all rounding through `round2()` in `lib/money.js` (half away from zero, same rule as PostgreSQL `round(numeric, 2)`). |
| Business dates | `date` (64 columns: inception, expiry, due, loss, receipt and voucher dates), returned to the application as `YYYY-MM-DD` strings (type parser 1082) so no time-zone shift can occur. |
| Instants | `timestamptz` (233 columns, e.g. `created_at`, `approved_at`, `sent_at`); no `timestamp without time zone` columns exist. |
| Flexible parts | `jsonb` (77 columns in 48 tables), see below. |
| Codes and statuses | `text` with application-level validation (zod, service rules) and 25 `CHECK` constraints; statuses are lower-case codes mapped to display labels through settings (for example `claims.status_labels`). |

## Document numbering

Document numbers are allocated by the SQL function `next_number(name, prefix, width = 5)`: it upserts the row `(name, year)` in the table `sequences`, increments `value` atomically (`INSERT ... ON CONFLICT DO UPDATE ... RETURNING`) and returns `<prefix>-<YYYY>-<value padded to 5>`. The counter restarts every calendar year; the prefix comes from the setting `numbering.<entity>.prefix` (43 numbering settings; `numbering_prefix()` reads them in SQL). When the number is taken inside the saving transaction (for example policy issue, quotations, receipts, disbursements), a rolled-back save also rolls back its number; helpers that take the number outside a transaction (claims, renewals, masters) can leave gaps after a failed save, and additionally re-check uniqueness against the target table. If gap-free numbering is a regulatory requirement for a document type (for example official receipts), this should be confirmed per document type.

{generate: number_sequences}

> **Gap:** `next_number()` takes the year from `now()` in the database session time zone (UTC on the local server and by default on RDS), not from the business time zone `general.timezone` (Asia/Manila). Documents created between 00:00 and 08:00 Manila time on 1 January are numbered in the previous year. Fix: compute the year with `now() AT TIME ZONE 'Asia/Manila'` (or the setting) or set the database / role time zone to Asia/Manila (recommended).

> **Note:** The numbering helper exists in four variants in the code (`documents/common.js`, `claims/util.js`, `masters/helpers.js`, `disbursements/service.js` `nextNo`), all calling the same SQL function; consolidating them in `lib/` is a code-quality improvement, not a correctness issue.

## Audit, history and soft delete

{widths: 26,74}
| Convention | Detail |
|---|---|
| Row stamps | `created_at` (79 tables), `updated_at` (62), `created_by` (59), `updated_by` (39). `updated_at` is set by the application; database triggers maintain it only on `users` and `roles` (`set_updated_at()`). |
| Audit log | `audit_log(id, at, user_id, username, entity, entity_id, action, before_data, after_data, ip)`, written by `lib/audit.js` from the route handlers of every create, update, approval, posting, run and sign-in related event; indexed on `(entity, entity_id)`. |
| Domain histories | `claim_history` (status), `claim_field_changes` (field-level), `renewal_activities`, `renewal_notices`, `collection_actions`, `remittance_approvals.history`, `login_history`, `password_history`, `job_runs`. |
| Soft delete | `leads` and `quotes` carry `deleted_at`; masters and product components use a `status` of `deleted` / `Deleted` (unique indexes are partial: `WHERE status <> 'deleted'`); financial documents are never deleted but cancelled or reversed (`receipts.cancelled_at`, journal reversal and correction vouchers `reversal_of`, `reversed_by_jv`, `correction_of`). A draft quotation is the only business record deleted physically. |
| Financial integrity | Trigger `jv_check_posting` refuses to post a journal voucher that has fewer than two lines, is unbalanced or has a zero total, or whose accounting period (`accounting_periods`) is closed. Trigger `gl_accounts_defaults` derives the normal balance of an account from its type. |

## Constraints and indexes

The schema has 226 indexes: 102 primary keys, 59 further unique indexes (business numbers, natural keys, partial uniqueness such as one open renewal per policy `renewals_open_policy_uq` or one pending approval per entity `remittance_approvals_open_uq`), 15 partial indexes and one GIN index. Case-insensitive uniqueness uses expression indexes on `lower(...)` (reinsurer names, treaty numbers, programme codes, template codes).

> **Gap:** 128 of the 174 foreign keys have no index whose leading column is the foreign-key column (list in document 03). Most are low-volume references to masters, but several are on growing tables and are used in joins or in lookups by parent: for example `job_runs.job_id` (queried by the scheduler on every run and by the run-history screen), `quotes.client_id`, `receipts.client_id`, `receipt_applications.receipt_id`, `remittance_lines.remittance_id`, `commissions.disbursement_id`, `incentive_results.calculation_id`. They also slow down deletes of parent rows. Recommended: add indexes for the FKs of transactional and log tables before the data volume grows (to be confirmed with a query-plan review in UAT).

## Sales and policy

![Sales and policy: leads, clients, quotations, policies, endorsements, payment captures](er_sales_policy)

A lead becomes a client when a quotation is converted (`clients.lead_id` is unique when set). A quotation references the lead or client, product, policy type, insurer and signatory; conversion creates the policy (`policies.quote_id`, `quotes.policy_id`). ## Billing, receipts and ledger

![Billing, receipts, collections and general ledger](er_finance_ledger)

A policy, endorsement or renewal raises a receivable (bill) with its booking journal (`receivables.booking_jv_id`). A receipt has lines per policy, and receipt applications allocate the lines to bills and link the posting journal. Collection items track follow-up of open bills. # Migrations

{widths: 26,74}
| Aspect | Implementation (`backend/src/db/migrate.js`) |
|---|---|
| Format | Plain SQL files `NNNN_name.sql` in `backend/src/db/migrations`, applied in file-name order. Numbers are grouped by area: 0001-0004 core, masters, operations, finance; 0010-0021 sales, claims, renewals; 0030-0034 ledger, receipts, disbursements, commission, petty cash; 0040-0044 configuration, product configurator, remittance, reinsurance, incentive; 0050 reports; 0060 security; 0070-0097 later changes (policy payments, chart of accounts, direct bill, security hardening, least-privilege reads, notification audience, principal insurer); 0110 branding. |
| Tracking | Table `schema_migrations(name, applied_at)`; a file is applied once. |
| Execution | On every API start (`server.js`), before the seed: each pending file runs in its own transaction together with its `schema_migrations` row; on error the transaction is rolled back and the API does not start. `npm run migrate` runs the same code; `npm run db:reset` drops and recreates the schema (development only). |
| Idempotency | Files use `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS` and guarded data updates, so a file partially applied by hand can be re-run. |
| Readiness | `GET /api/health` answers 503 until no migration is pending, so a load balancer does not route to an instance with an older schema. |
| Direction | Forward only (no down migrations). The go-live checklist states that migrations only add; rollback of data means restoring a snapshot (document 09). |

> **Recommended / to be confirmed by the business and DevOps:** With several instances starting together, two instances may try to apply the same pending file; the second fails on the unique `schema_migrations` row or on the DDL and restarts. Deploy with one instance first (as the checklist says) or add a PostgreSQL advisory lock around `migrate()` (small code change). Keep destructive changes (column drops, type changes) in a separate release after the code that no longer uses them is live.

# Seed data

`backend/src/db/seed.js` runs on every start after the migrations and with `npm run seed`. Every step is idempotent: rows are inserted by natural key or fixed id (`ON CONFLICT DO NOTHING / DO UPDATE` on descriptive columns), so administrator edits are kept.

1. In code: the 9 roles, 50 permissions (read / write for 25 modules), the role grants, and the administrator `BrokerVerse` (password from `ADMIN_PASSWORD`; without it a random password is generated, logged once and must be changed at first sign-in).
2. `seeds/settings.json` (configuration keys, inserted only if missing) and `seeds/jobs.json` (the 9 scheduled jobs).
3. Encryption of any two-factor secret still stored in clear (upgrade path).
4. The SQL files `seeds/*.sql` (**reference data**, always) and `seeds/sample/*.sql` (**sample data**, only when `SEED_SAMPLE_DATA` is on), interleaved by file name so a sample file runs after the reference file it depends on.

{widths: 24,76}
| Class | Content |
|---|---|
| Reference | Settings; roles and permissions; Philippine geography, districts and postal codes; currencies, banks, insurers, products and policy types; vehicle makes, models and variants; BI / PD / PA covers; head office branch; master screen registry and reference master records; chart of accounts (128 accounts) and main / sub account masters; product templates with the motor and CTPL tariff; report catalogue (19 reports); direct-bill and security configuration. |
| Sample | Fictional leads, clients, quotations, policies, endorsements, claims, renewals, receivables, receipts, collections, disbursements, petty cash, commissions and referrers, remittances, reinsurance, incentives, journal vouchers, demo branches, signatories and master records, and six sample users. |

`SEED_SAMPLE_DATA` accepts true / false (1 / 0, yes / no, on / off); unset, it is on in development and test and off with `NODE_ENV=production`. A database seeded with sample data is cleaned with `npm run purge:sample` (document 10).

# Time zone, date and amount handling

{widths: 26,74}
| Topic | Design |
|---|---|
| Storage | Instants in `timestamptz` (stored in UTC); calendar dates in `date`. The server and database run in UTC (local server `Etc/UTC`; the container images default to UTC). |
| Business date | `lib/dates.js`: "today" is the calendar date in `general.timezone` (seeded `Asia/Manila`), not the server's UTC date; `businessDate()`, `calendarPeriod()` and the report engine use the configured zone, so between 00:00 and 08:00 Manila time the system does not use yesterday's date. |
| Display | Front end formats dates with `general.date_format` (`DD/MM/YYYY`) through `utility/dateFormat.js`; amounts with the configured currency and locale (`useFormatCurrency`, `formatMoney()` on the server). |
| Money | `numeric` in the database, rounding by `round2()` (half away from zero with binary floating-point correction); taxes (VAT 12 %, DST 12.5 %, LGT 0.75 %) and commission rates come from settings. |

> **Gap:** A few SQL statements use the database date instead of the business date: the `policy-expiry` job (`expiry_date < current_date`), the `quote-expiry` job (`created_at < now() - interval`), the renewal pipeline (`current_date + days`) and `next_number()` (year). With the database in UTC, these run against the UTC date, which differs from the Manila date between 00:00 and 08:00 Manila time. Combined with the scheduler running in UTC (document 01), the daily jobs currently run at 08:15-16:00 Manila time, when the UTC and Manila dates agree, so the effect today is limited to the year boundary of document numbers; it becomes visible if the scheduler time zone is fixed without also fixing these statements. Recommended: set the database role's `timezone` to Asia/Manila (`ALTER ROLE ... SET timezone`) or pass the business date as a parameter.

> **Note:** Amounts are converted from `numeric` to JavaScript double-precision numbers. This is exact for amounts of up to about 90 trillion with two decimals, far above broking volumes, provided every arithmetic result is rounded with `round2()`, which the ledger and document code does.
