# Introduction

## Purpose and scope

This document describes the logical and physical design of the BrokerVerse OOTB database: the schema by business domain, the entity-relationship structure of each domain, the keys, the JSONB document columns, document numbering, audit and soft-delete conventions, the posting rules and period controls that protect the ledger, the migration and seed approach, and the handling of time zones, dates and amounts. The table-by-table inventory with sizes, row counts and retention classes is document 03.

Sources: `backend/src/db/migrations/*.sql` (139 files, 8,360 lines, plus the 10 migrations of packages B and G being merged), `backend/src/db/seeds`, `backend/src/db/pool.js`, `migrate.js`, `seed.js`, `backend/src/lib/dates.js`, `money.js`, `numbering.js`, and the catalogue of a PostgreSQL 16 database created for this issue on 04 October 2026: migrated with the migrations of the branch and of packages B and G and seeded with the reference data only (snapshot in `docs/architecture/tools/data/db_snapshot.json`).

## Database platform

{generate: db_facts}

One database and one schema (`public`) hold all data. The application connects with a single login through `DATABASE_URL` (node-postgres pool, maximum 10 connections per API process). The login needs the right to create tables because the API applies its own migrations on start. The database time zone is set to `Asia/Manila` (`ALTER DATABASE ... SET timezone`, or the RDS parameter group), as `deploy/README.md` requires. Only the `pgcrypto` extension is used, for `gen_random_bytes()` in primary-key defaults.

# Schema overview by domain

The 260 tables fall into 25 domains (250 tables without packages B and G). Row counts and sizes are those of the reference data a new database starts with; transaction tables are empty.

# Design conventions

## Keys

{widths: 26,74}
| Convention | Detail |
|---|---|
| Business records | 103 tables use a text primary key made of a readable prefix and random hexadecimal characters generated by the database, for example `policies.id DEFAULT 'pol_' \|\| encode(gen_random_bytes(8), 'hex')`. Prefixes include `ld_` lead, `cl_` client, `qt_` quotation, `bs_` broker slip, `ofr_` insurer offer, `plc_` placement, `pol_` policy, `end_` endorsement, `clm_` claim, `rnw_` renewal, `or_` receipt, `jv_` journal voucher, `pv_` payment voucher, `rm_` remittance, `dn_` debit note, `brc_` bank reconciliation, `yec_` year-end run, `usr_` user and `doc_` document. | Reference, line and log tables | 125 tables use integer or bigint serial keys: masters (countries, banks, insurers, products), lines and logs that grow fast (`journal_lines`, `audit_log`, `login_history`, `job_runs`, `claim_history`, `risk_participants`, `bank_rec_match_items`, `period_status_history`). |
| Natural and composite keys | 32 tables: `app_settings(key)`, `gl_accounts(code)`, `master_types(code)`, `report_definitions(code)`, `accounting_periods(period)`, `fiscal_years(code)`, `tax_codes(code)`, `bank_statement_formats(code)`, `bank_transaction_types(code)`, `bank_match_rules(code)`, `period_close_checklist(code)`, `opening_balances(fiscal_year, account_code)`, `receivable_participants(receivable_id, insurance_company_id)`, `refresh_tokens(jti)`, `schema_migrations(name)`, `sequences(name, period)`, `role_permissions`, `user_roles` and others. |
| Business numbers | Readable document numbers (`QT-2026-00001`, `POL-2026-00001`, `OR-2026-00019`, `BS-`, `PS-`, `MEC-`, `BRC-`) are separate unique columns (`quote_number`, `policy_number`, `receipt_number`, `slip_number`, `run_number`...), never primary keys. Most detail endpoints accept either the id or the number. |
| Foreign keys | 468 foreign keys: 369 `NO ACTION` (a referenced record cannot be deleted while in use), 77 `CASCADE` (children with no meaning without their parent: journal lines, receipt lines, match items, claim history, renewal notices, role grants, refresh tokens, notifications) and 22 `SET NULL`. |

## Column types

{widths: 26,74}
| Data | Type and handling |
|---|---|
| Amounts | `numeric` (490 columns), typically `numeric(14,2)`; converted to JavaScript numbers by the pool type parser; all rounding through `round2()` in `lib/money.js` (half away from zero, the same rule as PostgreSQL `round(numeric, 2)`). Shares are `numeric(7,4)`. |
| Business dates | `date` (217 columns: inception, expiry, due, loss, receipt, voucher, statement and period dates), returned to the application as `YYYY-MM-DD` strings so no time-zone shift can occur. | Instants | `timestamptz` (590 columns, for example `created_at`, `approved_at`, `sent_at`); there are no `timestamp without time zone` columns. |
| Flexible parts | `jsonb` (166 columns in 103 tables), see below. |
| Codes and statuses | `text` with validation in the application (zod, service rules) and 390 `CHECK` constraints; statuses are lower-case codes mapped to display labels. |

## Document numbering

Every document number comes from a series in the Document Numbering master (`document_numbering`, 85 series, Master > Document Numbering). `nextDocumentNumber(code, { db })` in `lib/numbering.js` calls the SQL function `next_document_number(code, branch, lob, date)`. The function locks the counter row of the series and period in `sequences` until the caller's transaction ends, so two users never get the same number and a rolled-back save gives its number back. `format_document_number()` applies the pattern: tokens `{PREFIX} {YYYY} {YY} {MM} {FY} {BRANCH} {LOB} {SEQ}`; all seeded series use `{PREFIX}-{YYYY}-{SEQ}`. A prefix must be unique among active series (index `document_numbering_active_prefix`); migration 0246 lets a series start a period at the old system's next number at go-live. The reset rule of a series is `yearly`, `fiscal_yearly`, `monthly` or `never`; the counter period is `2026`, `FY2027`, `2026-09` or `ALL`. The year is taken from the business date in `general.timezone`, so a document created at 00:30 Manila time on 1 January gets the new year. The next number of a series can only be moved forward (for example to continue from the legacy system at go-live). A trigger copies each prefix into the read-only setting `numbering.<code>.prefix`.

## Audit, history and soft delete

{widths: 26,74}
| Convention | Detail |
|---|---|
| Row stamps | `created_at` (192 tables), `updated_at` (148), `created_by` (157), `updated_by` (107). `updated_at` is set by the application; triggers maintain it on `users`, `roles`, `commission_rates` and `document_numbering` (`set_updated_at()`). |
| Audit log | `audit_log(id, at, user_id, username, entity, entity_id, action, before_data, after_data, ip, source)` (`source`, migration 0247: screen, API or job), written by `lib/audit.js` from every create, update, approval, posting, run and sign-in related event; indexed on `(entity, entity_id)`, `(at)` and `(username)`. |
| Domain histories | `claim_history`, `claim_field_changes`, `renewal_activities`, `renewal_notices`, `collection_actions`, `remittance_approvals.history`, `period_status_history`, `bank_reconciliation_history`, `login_history`, `password_history`, `job_runs`. |
| Soft delete | `leads`, `quotes` and `bank_statements` carry `deleted_at`; masters and product components use a `status` of `deleted` (unique indexes are partial: `WHERE status <> 'deleted'`). Financial documents are never deleted but cancelled or reversed (`receipts.cancelled_at`, journal reversal and correction vouchers, `bir_2307_certificates.cancelled_at`). A draft quotation is the only business record deleted physically. |

## Ledger integrity

{widths: 26,74}
| Control | Detail |
|---|---|
| Posting rules | Every system journal is built by `postEvent()` from the posting rule of its business event (43 events with an active rule, for example `policy.issue.broker_billed`, `ap.invoice`, `fa.depreciation`, `sales_invoice.issue`, `override_commission.accrual`, `receipt.apply`, `remittance.settlement`, `claim.funds_received`, `commission.clawback`). A rule has versions with an effective date (`posting_rules`) and lines (`posting_rule_lines`) that name either a GL account or an account role. Account roles resolve to GL accounts through the settings `accounting.account.<role>` (Account Determination). A line marked per participant is split across the co-insurers by share, with the rounding remainder on the lead. |
| Balance and period trigger | Trigger `jv_check_posting` refuses to post a journal voucher with fewer than two lines, unbalanced, with a zero total, or in a period that does not accept postings. |
| Period status | `accounting_periods` holds periods 1 to 12 and the adjustment period 13 of each fiscal year with the status `open`, `soft_closed`, `closed` or `locked`. Trigger `accounting_period_lock_guard` refuses to reopen a period locked by the year-end close. Every change is written to `period_status_history`. |
| Opening balances | The year-end close writes the balance-sheet balances into `opening_balances` of the next year; the go-live import writes the old system's trial balance there (source `go-live:<date>`). Reports read them through `pe_balance_before()`; no opening journal is posted. |
| Co-insurance | `risk_participants` holds the participants of a broker slip, quotation, placement or policy (one lead, shares total 100%, index `risk_participants_one_lead`); `receivable_participants` and `remittance_allocations` split bills and collections per insurer. |
| Account defaults | Trigger `gl_accounts_defaults` derives the normal balance of an account from its type. |

## Constraints and indexes

The schema has 901 indexes: 260 primary keys, 180 further unique indexes (business numbers, natural keys and partial uniqueness such as one open renewal per policy, one pending approval per entity, one active close run per period, one lead co-insurer per record), 71 partial indexes and one GIN index. Case-insensitive uniqueness uses expression indexes on `lower(...)`.

Migration `0146_foreign_key_indexes.sql` indexed the foreign keys of every table that grows (transactions, documents, lines and logs) and added the operational log indexes `job_runs (job_id, started_at)`, `email_outbox (status, created_at)`, `audit_log (at)` and `audit_log (username)`. The list was produced by `backend/scripts/fk-index-report.js`. 60 of the 468 foreign keys have no index whose first column is the foreign-key column; they are on small master and set-up tables (vehicle models, states, policy types, product components) or are maker-checker stamp columns (`approved_by`, `rejected_by`), left out on purpose. They are listed in document 03.

## Sales and policy

![Sales and policy: leads, clients, quotations, policies, endorsements, payment captures](er_sales_policy)

A lead becomes a client when a quotation is converted (`clients.lead_id` is unique when set). A quotation references the lead or client, product, policy type, insurer and signatory; conversion creates the policy (`policies.quote_id`, `quotes.policy_id`). A renewed policy points to its predecessor (`policies.renewed_from`, `renewed_to`). Endorsements belong to a policy and may raise their own bill (`endorsements.receivable_id`). `policy_payments` holds payments captured by front-office staff until Accounting confirms them and issues a receipt.

## Placement and co-insurance

![Placement: broker slips, insurer offers, placement slips and co-insurance participants](er_placement)

A broker slip is created from a lead or client and sent to several insurers; each answer is an `insurer_offers` row (premium, rate, taxes, deductibles, validity, share offered) or a decline. The chosen offers become a quotation or a placement slip (`placements.broker_slip_id`, `placements.quote_id`). A placement is sent to the lead insurer and the co-insurers; each participant binds with its own reference and the policy is issued when all have bound (`placements.policy_id`). `risk_participants` is shared by all four record types through `entity_type` and `entity_id`.

![Renewals: renewal cases, quotes, notices, activities, batches, win-back campaigns](er_renewals)

## Billing, receipts and collections

![Billing, receipts, credits, co-insurance split and collections](er_billing)

A policy, endorsement or renewal raises a receivable (bill) with its booking journal (`receivables.booking_jv_id`). A receipt has lines per policy, and receipt applications allocate the lines to bills and link the posting journal. Return premium and cancellations reduce a bill through `receivable_credits`. Collection items track the follow-up of open bills; write-offs use the reasons and GL accounts of `write_off_reasons`.

## General ledger and posting rules

![General ledger: chart of accounts, journals, periods, matching and posting rules](er_ledger)

Journal vouchers hold balanced journal lines coded to the chart of accounts (`gl_accounts`). Open-item accounts are reconciled by `entry_matches` (debit line to credit line). Journals point back to their source document through `journal_vouchers.reference_type` and `reference_id`.

## Period end and tax

![Period end: fiscal years, close runs, recurring journals, year-end, tax codes and BIR 2307](er_period_end)

## Bank reconciliation

![Bank reconciliation: statement formats, statements and lines, matches, reconciliations](er_bank_reconciliation)

A bank statement is imported with a statement format into `bank_statements` and `bank_statement_lines` (a line hash refuses duplicates). Matches link bank lines to cash-account journal lines (`bank_rec_match_items` with a `side`). A monthly reconciliation (`bank_reconciliations`) stores the statement figures and, once approved, locks the matches cleared up to the period end. The bank account itself is a master record linked to a GL cash account.

## Commission and incentive

![Commission lines, adjustments, the rate matrix, referrers and incentive programmes](er_commission_incentive)

Commission lines are created per policy, endorsement and referrer in the referral chain (`commissions_policy_referrer_uq`), link to the accrual and payment journals and to the payment voucher that paid them. `commission_adjustments` records the reversal or clawback when premium is returned. The rate of a new policy comes from `commission_rates` (insurer, product, line, policy type, effective dates), else the insurer's default rate. Referrers form a hierarchy (`parent_referrer_id`); they do not sign in.

## Remittance and direct bill

![Remittances to insurers, co-insurance allocations, insurer refunds and direct-bill debit notes](er_remittance_directbill)

Broker-billed premium is remitted to insurers through `remittances` with `remittance_lines` per policy; settlements, adjustments and exceptions are `remittance_items`; `remittance_approvals` is a multi-level approval register (entity, levels, SLA, history). For a co-insured policy `remittance_allocations` splits each collection by insurer share. `insurer_refund_credits` holds refunds due from an insurer on returned premium already remitted; they are netted against the next remittance. Direct-billed policies produce `direct_bill_items` (commission receivable) billed to the insurer on `commission_debit_notes` and settled by `commission_debit_note_collections`.

## Compliance

![AML/CFT, Insurance Commission registers, complaints, breaches and data privacy](er_compliance)

The AML tables hang off `clients`: KYC records of juridical clients, risk assessments and EDD reviews, screenings and their hits against the screening lists, alerts raised by monitoring rules, cases and AMLC report files. Package B adds the licence register, fit and proper records, the IC statement mapping, the complaints register and the breach register. With package B, TIN, ID and bank account numbers are encrypted in the database by the triggers `pii_protect_columns` and `pii_protect_json` with blind indexes (`*_bidx`) for exact search (document 05).

## Integrations

![Integration framework: connectors, outbox, attempts, inbox, messaging, CTPL, insurer mappings and bank payment files](er_integration)

Every message to a third party is a row of `integration_outbox` written in the business transaction; `integration_attempts` keeps each try and `integration_inbox` each message received. Connectors keep only the names of the environment variables that hold their credentials.

| Aspect | Implementation (`backend/src/db/migrate.js`) |
|---|---|
| Format | Plain SQL files `NNNN_name.sql` in `backend/src/db/migrations`, applied in file-name order: 0001-0004 core, masters, operations, finance; 0010-0021 sales, claims, renewals; 0030-0034 ledger, receipts, disbursements, commission, petty cash; 0040-0050 configuration, product configurator, remittance, reinsurance, incentive, reports; 0060-0097 security and later changes; 0110-0113 branding and the Company letterhead; 0115-0117 role inheritance and bank reconciliation; 0120-0127 co-insurance, document numbering, commission rates, insurer credit terms, placement; 0130-0136 posting rules, period end, tax codes; 0140-0152 broker roles, business-date defaults, foreign-key indexes, accounting follow-ups, go-live imports and the e-mail sender. |
| Tracking | Table `schema_migrations(name, applied_at)`; a file is applied once. |
| Execution | On every API start (`server.js`), before the seed. The migrate step first takes the advisory lock `hashtext('brokerverse.migrate'), hashtext('schema_migrations')`; instances that start together wait (up to `MIGRATION_LOCK_TIMEOUT_MS`, 10 minutes) and then find nothing to do. Each pending file runs in its own transaction with its `schema_migrations` row; on error the transaction is rolled back and the API does not start. `npm run migrate` runs the same code; `npm run db:reset` drops and recreates the schema (development only). |
| Idempotency | Files use `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ON CONFLICT DO NOTHING` and guarded updates, so they are safe on a database that already holds data. An applied file is never edited; fixes go forward in a new file. |
| Readiness | `GET /api/health` answers 503 until no migration is pending, so a load balancer does not route to an instance with an older schema. |
| Direction | Forward only. Migrations only add; rolling back data means restoring a snapshot (document 09). |

> **Recommended / to be confirmed by the business and DevOps:** Keep destructive changes (column drops, type changes) in a separate release after the code that no longer uses them is live. Start one instance first when a release contains migrations (`deploy/REFERENCE.md`, Upgrading).

# Seed data

`backend/src/db/seed.js` runs on every start after the migrations and with `npm run seed`. Every step is idempotent: rows are inserted by natural key or fixed id, so administrator edits are kept.

1. In code: the roles, permissions and grants, and the administrator `BrokerVerse` (password from `ADMIN_PASSWORD`; without it a random password is generated, logged once and must be changed at the first sign-in).
2. `seeds/settings.json` (configuration keys, inserted only if missing) and `seeds/jobs.json` (the scheduled jobs; the period-end and bank-matching jobs come from migrations).
3. Encryption of any two-factor secret still stored in clear (upgrade path).
4. The SQL files `seeds/*.sql` (**reference data**, always) and `seeds/sample/*.sql` (**sample data**, only when `SEED_SAMPLE_DATA` is on), interleaved by file name so a sample file runs after the reference file it depends on.

# Time zone, date and amount handling

{widths: 26,74}
| Topic | Design |
|---|---|
| Storage | Instants in `timestamptz` (stored in UTC); calendar dates in `date`. The database time zone is `Asia/Manila`; the containers run in UTC. |
| Business date | `lib/dates.js`: "today" is the calendar date in `general.timezone` (seeded `Asia/Manila`), not the server's UTC date. `businessDate()`, `calendarPeriod()`, the report engine, document numbering and the column defaults (`numbering_business_date()`, migration 0145) use the configured zone, so between 00:00 and 08:00 Manila time the system never uses yesterday's date. |
| Job times | The scheduler reads cron expressions in `general.timezone`: `0 6 * * *` runs at 06:00 Manila time. |
| Display | The front end formats dates with `general.date_format` (`DD/MM/YYYY`) and amounts with the configured currency and locale (`en-PH` grouping); the server uses `formatMoney()` and the PDF engine the same settings. |
| Money | `numeric` in the database, rounding by `round2()`; taxes (VAT 12%, DST 12.5%, LGT 0.75%, expanded withholding by ATC) and commission rates come from settings, the tax codes and the rate matrix. |

> **Note:** Amounts are converted from `numeric` to JavaScript double-precision numbers. This is exact for amounts of up to about 90 trillion with two decimals, far above broking volumes, provided every arithmetic result is rounded with `round2()`, which the ledger and document code does.
