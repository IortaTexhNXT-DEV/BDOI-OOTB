# Introduction

## Purpose and scope

This document proposes the recovery time objective (RTO) and recovery point objective (RPO) for BrokerVerse OOTB, explains how the recommended architecture meets them for each failure scenario, and lists what must be in place and tested for the objectives to hold. Backup configuration and restore procedures are in document 09; the high-availability design in document 07.

> **Recommended / to be confirmed by the business and DevOps:** All objectives in this document are proposals. The business owner must confirm them against the impact of an outage on premium collection, claims service and regulatory reporting, and DevOps must confirm that the provisioned services (retention, Multi-AZ, cross-region copies) and the tested restore times meet them. Nothing in the baseline code or configuration sets an RTO or RPO.

## Definitions

- **RPO** (recovery point objective): the maximum period of committed data that may be lost, measured back from the incident.
- **RTO** (recovery time objective): the maximum time from the declaration of the incident until users can work again.
- **Service tiers**: groups of functions or data with the same objectives.

# Business impact and service tiers

| Tier | Functions and data | Rationale |
|---|---|---|
| Tier 1: core transactions | Sign-in; quotations, broker slips, placements, policies, endorsements, claims; bills, receipts, journals, vouchers, commissions, remittances, debit notes, bank reconciliations, period closes (PostgreSQL) | Financial and contractual records; loss requires re-keying from paper and bank evidence and may breach record-keeping duties |

| Tier 3: operational and derived data | Notifications, e-mail outbox, generated report files, scheduler history, dashboards | Regenerated by jobs or re-run by users |
| Tier 4: front end and configuration as code | SPA build, backend image, migrations, seeds | Rebuilt from Git and the pipelines |

# Proposed objectives

{widths: 26,15,15,44}
| Scenario | RPO | RTO | How the architecture meets it |
|---|---|---|---|
| API container failure | 0 | < 5 min (typically seconds) | At least two API containers behind the load balancer; a failed container is replaced by the container service; no data is held in the container |
| Availability Zone failure | 0 (Tier 1 and 2) | < 15 min | RDS Multi-AZ synchronous standby, automatic failover in 1 to 2 minutes; EFS regional storage; containers in the second AZ keep serving |
| Database instance or storage failure | 0 (Multi-AZ) | < 15 min | Multi-AZ failover; without Multi-AZ: restore from PITR (RPO about 5 min, RTO 1 to 2 h) |
| Logical corruption or erroneous mass change (bad release, wrong purge, user error) | <= 15 min (target 5 min) | <= 4 h | PITR to a new RDS instance just before the incident, verification, switch of `DATABASE_URL`; transactions entered after the recovery point are re-entered from the audit trail and source documents |
| Loss or corruption of uploaded files | <= 24 h | <= 4 h | AWS Backup of EFS (daily); files of the day after the last backup must be re-uploaded; EFS restore to a new path or file system |
| Regional outage (ap-southeast-1 unavailable) | <= 24 h (daily cross-region copies) | <= 24 h (warm standby: 8 h) | Restore the latest cross-region RDS snapshot and EFS recovery point in the recovery region, deploy the same images and the SPA, repoint DNS / CloudFront |
| Accidental deletion of the front end | 0 | < 1 h | S3 versioning or re-run of the pipeline on the last commit, CloudFront invalidation |
| Loss of secrets | n/a | < 1 h | Secrets Manager versions; sealed escrow copy of `DATA_ENCRYPTION_KEY` and `JWT_SECRET` (document 09) |

Summary proposal for the business: **Tier 1 RPO <= 15 minutes (5 minutes achievable with PITR) and RTO <= 4 hours for a restore; RTO <= 15 minutes for infrastructure failures in the region; Tier 2 RPO <= 24 hours; regional disaster RPO <= 24 hours and RTO <= 24 hours.**

# How the objectives are achieved

## Recovery point

- **Amazon RDS automated backups** keep daily snapshots and the transaction log (WAL), uploaded about every five minutes, for the retention period (recommended 35 days, the RDS maximum); a point-in-time restore is possible to any second up to the latest restorable time, normally within five minutes of the present. This gives the Tier 1 RPO of 5 to 15 minutes.
- **Multi-AZ** replicates synchronously to the standby, so an instance or AZ failure loses no committed transaction (RPO 0).
- **Cross-region snapshot copies** (daily) bound the loss in a regional disaster to one day. If the business needs less, use cross-region automated backup replication (continuous, PITR in the second region) or an RDS cross-region read replica (seconds).
- **EFS** is backed up daily by AWS Backup; files are the Tier 2 RPO driver. If daily is not enough, schedule additional EFS backups (for example every 4 hours) or move documents to S3 with versioning and cross-region replication (later change).
- The application writes each business operation in one transaction, so every recovery point is transactionally consistent; e-mails and notifications created after the recovery point are simply not present.

## Recovery time

- Infrastructure failures are handled automatically (load balancer health checks, container replacement, RDS failover) within minutes.
- Restores (PITR, snapshot) create a new RDS instance; for a database of a few GB (document 06) the restore itself takes about 20 to 60 minutes; the remaining RTO covers verification, switching `DATABASE_URL`, restarting the containers and business checks. On a restored database of the same release the API finds no pending migration, re-runs the idempotent seed and becomes ready as soon as it connects.
- Recovery in another region requires the images (ECR replication), secrets and infrastructure definitions to exist there; with infrastructure as code (recommended) the environment can be created in 2 to 4 hours, with a pre-built warm standby in under 1 hour plus data restore.

# Testing and review

{widths: 32,24,44}
| Test | Frequency (recommended) | Evidence |
|---|---|---|
| RDS point-in-time restore to a new instance, application smoke test against it | Quarterly and before go-live | Restore duration, recovery point reached, smoke test result |
| Multi-AZ failover (`reboot with failover`) in UAT | Twice a year | Failover time, errors seen by users |
| EFS restore of a sample of files | Quarterly | Files readable through the application |
| Regional recovery exercise (tabletop yearly, full every two years) | Yearly | Achieved RTO / RPO against the objectives |
| Review of objectives with the business | Yearly or after major change | Signed-off objectives |
